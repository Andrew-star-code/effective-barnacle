# ADR 0016. Сотрудник опознаётся по objectGUID, смена email переносится в WeKnora

Статус: принято · Дата: 13.11.2026 · Источник: SPEC §6.1, §7.4, решение № 30

## Контекст

При входе по OIDC WeKnora `v0.9.0` ищет пользователя по email (`GetUserByEmail`), а если не находит — создаёт нового (`provisionOIDCUser`). API смены email в административных маршрутах нет: только создание, статус и сброс пароля.

Email в AD меняется, например при смене фамилии. После этого сотрудник вошёл бы в новую пустую учётку и потерял чаты и личные базы знаний.

## Решение

- Ключ сотрудника в `corp-ext` — `objectGUID` (`corp.user_profiles.ad_guid`).
- При смене `mail` в AD `corp-ext` обновляет `users.email` в БД WeKnora напрямую, с записью в аудит; синхронизация этого пользователя запускается сразу, а не раз в час.
- На пилоте проверить, отключается ли автосоздание пользователя при OIDC-входе. Если да — вход до синхронизации даёт ошибку, а не дубликат. Если нет — `corp-ext` находит дубликаты по `objectGUID` и показывает их в `corp-admin`.

## Отвергнутые альтернативы

- Только email как ключ — потеря данных при смене email.
- Синтетический неизменяемый email из GUID в claims Keycloak — ни строки кода, но в интерфейсе WeKnora сотрудник видит бессмысленный адрес.
- Патч с эндпоинтом смены email — ещё одна строка реестра ради одного `UPDATE`.

## Последствия

Ещё одно исключение из правила «`corp-ext` не пишет в таблицы WeKnora» (SPEC §16.2); при обновлении WeKnora сверяется колонка `users.email` и её ограничения. Слияние уже возникших дубликатов — ручная операция.
