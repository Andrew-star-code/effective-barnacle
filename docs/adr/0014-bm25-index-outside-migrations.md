# ADR 0014. Русский BM25-индекс — шагом provision, а не миграцией в форке

Статус: принято · Дата: 13.11.2026 · Источник: SPEC §11.2, решение № 28

## Контекст

Штатный BM25-индекс `embeddings_search_idx` собран с токенизатором `chinese_lindera` (`migrations/versioned/000002_embeddings.up.sql`). Для русского нужен стеммер, нижний регистр и стоп-слова. Первая редакция ТЗ предлагала патч P-01 — новую миграцию в `migrations/versioned/` форка.

WeKnora применяет миграции через golang-migrate со сквозной нумерацией; в `v0.9.0` последняя — `000134`. Наша `000135` при обновлении совпала бы по номеру с апстримной: база уже считает версию применённой, и чужая миграция была бы молча пропущена.

## Решение

Индекс пересоздаёт идемпотентный шаг `provision --search-index` в `corp-ext`: сравнивает определение индекса с нужным и пересоздаёт его при расхождении. Шаг выполняется после миграций WeKnora при каждой выкатке и обновлении. P-01 остаётся в реестре для учёта и для пулл-реквеста в WeKnora (токенизатор из переменной окружения); после принятия шаг удаляется.

## Отвергнутые альтернативы

- Миграция в форке — конфликт номеров и молча пропущенные миграции апстрима.
- Миграция с номером «с запасом» (например, `900001`) — golang-migrate после неё не применит апстримные миграции с меньшими номерами.

## Последствия

В форке нет ни одного файла ради P-01; шаг применим уже на пилоте. Появляется ещё одно исключение из правила «`corp-ext` не меняет БД WeKnora» (SPEC §16.2), и роли `corp-ext` нужно право на DDL этого индекса. Если апстримная миграция когда-нибудь пересоздаст индекс, шаг вернёт русский токенизатор при следующей выкатке; `eval/rag` это проверяет. На пилоте нужно убедиться, что запросы поиска не привязаны к `chinese_lindera` на своей стороне.
