### Находки при подъёме WeKnora в dev (14.11.2026)

Проверено запуском (UI и API, учётка из `deploy/compose/.env.example`):

- Признак `is_default` в `builtin_models.yaml` не задаёт модель встроенным агентам: у «Quick Answer» и «Smart Reasoning» в новом пространстве пустой `model_id`, чат отвечает «Agent не готов». Значит, раскладка (`provision`, этап 1–2) должна проставлять модель агентам каждого личного пространства — через `PUT /api/v1/agents/{id}` это работает.
- Режим агента со включёнными базами знаний требует модель реранжирования; без `rerank` в dev-стеке «Smart Reasoning» не запускается. Временно в dev у агента выключены базы (`kb_selection_mode: none`). Нужен `rerank` на CPU (§18.1) — следующий шаг этапа 0.
- Непереведённые строки при `DEFAULT_LOCALE=ru-RU`: «Go to configure →», «Edit Agent», «Model Config», «Basic Info», «Select Agent», «Built-in Agents», «Setup needed», названия встроенных агентов в подписи поля ввода («Smart Reasoning»), описания агентов приходят с бэкенда на английском. Вход в P-08/P-07 (этап 2).
- Ссылки на github.com и weknora.weixin.qq.com на странице входа — убрать вместе с остальным лишним (§17.2).

Профиль `builtin_models.ollama.yaml` (`qwen3.5:9b`, `bge-m3`) — проверено запуском 14.11.2026 на RTX 5070 12 ГБ (база «Кадры (тест)» с одним вымышленным положением об отпусках):

- Контейнер WeKnora достаёт до Ollama на хосте через `host.docker.internal` (Docker Desktop, Ollama слушает только `127.0.0.1`); каталог обновляется на месте при смене профиля.
- «Smart Reasoning» на `qwen3.5:9b`: ответ на русском стримом, размышления — отдельным блоком, название чата сгенерировано на русском. Модель целиком на GPU (~9 ГБ занято с контекстом 32K).
- Первый ответ — около минуты (загрузка модели и размышления); параллельные запросы Ollama ставит в очередь.
- **Размышления не выключались.** У провайдера `generic` по умолчанию `thinking_format: none` — WeKnora не передаёт «выкл» вообще, а `qwen3.5` в Ollama по умолчанию размышляет. Следствие хуже, чем лишняя задержка: служебные генерации с лимитом 1024 токена (описание документа, вопросы к фрагментам) целиком уходили в размышления, ответ пустой, задача повторялась и падала; описание документа заменялось первыми строками текста. Исправлено в профиле: `spec.compat.thinking_format: openai` + `thinking_levels.off: none` — Ollama понимает только `reasoning_effort: "none"`, а `think: false` и `chat_template_kwargs` игнорирует (проверено запросами напрямую). **Для прода (этап 2):** у каждой модели в `builtin_models.yaml` явно задать формат thinking под vLLM (`chat-template-kwargs`) и проверить служебные генерации — это пилотный пункт 7.
- `qwen3.5:9b` (4 бита) примерно в 1 из 4 ответов теряет закрывающую `}` в JSON описания документа при `finish_reason=stop`; с `response_format: json_object` — нет. WeKnora при этом повторяет задачу, после исчерпания попыток ставит описание-заглушку. На прод-модели проверить; если повторится — кандидат в патч (передавать `response_format` для структурированных генераций).
- Индексация на `bge-m3` + `qwen3.5:9b` после исправления: markdown-документ разобран на 7 фрагментов; описание, профиль (тема, тип, типичный вопрос) и вопросы к фрагментам — на русском (`WEKNORA_LANGUAGE=ru-RU` работает для служебных генераций).
- «Быстрый ответ» по базе: верный ответ на русском со ссылкой на источник; клик открывает документ с подсвеченным пунктом. Запрос с точным кодом договора (`СКЛ-7741/26`) находит документ — но в базе один документ, это не проверка BM25 (пилотный пункт 23 — на 200 документах). В одном ответе модель добавила деталь, которой нет в документе, — материал для `eval/rag`.
- Вызов инструментов реальной моделью не проверен: режим агента с базами знаний требует реранкер, а его в dev-стеке нет.

### Русский BM25-индекс, P-01 (14.11.2026)

SQL пересоздания индекса — [`search_index.sql`](../services/corp-ext/app/modules/provisioning/sql/search_index.sql); тот же войдёт в `provision --search-index` (этап 3). Проверено запуском на dev-стеке (ParadeDB `pg_search` 0.25.11, база «Кадры (тест)», 29 строк в `embeddings`):

- **До:** индекс из миграции `000002` (`chinese_lindera` через legacy `text_fields`) не приводит текст к нижнему регистру и не стеммит: «отпуска», «отпусков» и «Отпуск» находят три разных набора фрагментов.
- **После** (`pdb.simple('stemmer=russian', 'stopwords_language=russian')`, ID-поля — `pdb.literal`): «отпуска», «отпусков», «Отпуск», «ОТПУСКАМИ» находят один и тот же набор; стоп-слово «и» не находит ничего; «ё» сводится к «е» стеммером; код `СКЛ-7741/26` находится (разбивается на `скл`, `7741`, `26`, как и раньше).
- Поиск самой WeKnora (`POST /knowledge-bases/{id}/hybrid-search`, только ключевые слова) с новым индексом работает, включая фильтр по базе: «ОТПУСКАМИ без содержания» → пункт про отпуска без сохранения зарплаты, «путевка в санаторий» → раздел о санаторно-курортном лечении.
- Индекс переживает перезапуск WeKnora с `AUTO_MIGRATE=true`: миграция `000002` создаёт индекс, только если его нет.
- Пилотный пункт 23, первая половина — **ответ:** запросы WeKnora (`content ||| :query`) разбираются токенизатором индекса и к `chinese_lindera` не привязаны (проверено по коду и запуском). Вторая половина — hit@5 до и после на 200 документах — ещё не измерена.
- Ограничение: английские слова в документах не стеммятся (один стеммер на поле). Если в базах заметная доля английского — решать по eval.

### hit@5 до и после P-01 (14.11.2026)

Проверено запуском на тестовом стеке с чистыми томами, профиль Ollama (`bge-m3`, описания — `qwen3.5:9b`, реранкер — `bge-reranker-v2-m3` на CPU). Корпус — открытый `wikifacts-articles_v0` (RusBEIR, статьи русской Википедии): 200 статей, в среднем 2 913 слов, 7 786 фрагментов; 96 запросов-фактов, у каждого все релевантные статьи в выборке (seed 42). Метрики — на уровне документов, `/knowledge-search`, 20 кандидатов. Скрипт и порядок прогона — [`eval/rag/`](../eval/rag/README.md).

| --- | --- | --- | --- | --- | --- |
| BM25 | 0,906 | **0,969** | 0,848 | **0,932** | 0,20 → 0,02 с |
| Векторы | 0,979 | 0,979 | 0,912 | 0,912 | 0,08 с |
| Гибрид | 1,000 | 1,000 | 0,931 | **0,988** | 0,24 → 0,07 с |

Для сравнения с реранком — гибрид на тех же 30 запросах: MRR 0,956 до и 0,983 после.

- P-01 работает: промахи штатного BM25 — словоформы («пушкинский биф», «бортовом компьютере»), стеммер их закрывает. Гибрид после P-01 сравнялся с гибридом с реранком; реранк поверх почти ничего не добавляет.
- Корпус проще корпоративного: BM25 на wikifacts очень силён (так и в статье RusBEIR), hit@5 упирается в потолок. Абсолютные цифры не переносить на свои документы; тот же прогон повторить на них.
- Реранк на CPU — около 40 с на запрос с 20 кандидатами; в проде — GPU (§3.3).
- Описания документов получили только 85 из 200 статей. Причина не разбиралась — посмотреть на этапе 3 вместе с пунктом 13.

**Находка — баг WeKnora, патч P-12.** В базе знаний с выключенной генерацией вопросов (значение по умолчанию) WeKnora добавляет к BM25-запросу фильтр-исключение сгенерированных вопросов (`substr(source_id, …)`). ParadeDB 0.25.11 в выборке top-N его не поддерживает — «Unsupported query shape». Ключевой поиск падает на каждом запросе; гибрид молча идёт только по векторам, в логе — ERROR. Индекс P-01 и добавление колонок фильтра в индекс не помогают (проверено в psql). В upstream `main` на 14.11.2026 не исправлено. Для замера у тестовой базы флаг `question_generation_config.enabled` включён прямо в БД тестового стека (вопросы не генерировались, документы уже были проиндексированы). Без P-12 «до» в WeKnora по умолчанию — это строка «Векторы».

Цена решений: исключений из правила «`corp-ext` не меняет БД WeKnora» стало четыре вместо двух (SPEC §16.2), а `corp-ext` оказался на пути потока ответа чата.

Замечания без решения:

- P-02 читает `corp.user_profiles` из Go-кода WeKnora — ядро начинает зависеть от нашей схемы; для пулл-реквеста в апстрим источник значений придётся абстрагировать.
- `JWT_SECRET` общий с `corp-ext` (HS256): владелец секрета может и выпускать токены. Отражено в ADR 0012.
- Ссылки на карточки моделей в SPEC §3.3 частично ведут на вторичные источники (`dell.huggingface.co`, `sotaverified.org`, Википедия). Параметры моделей и флаги vLLM перепроверить по первоисточникам перед бенчмарком.
- `corp-admin`: TypeScript 7 несовместим с `vue-tsc`; мажорные версии выровнены с фронтендом WeKnora (TS 6, Vite 7, Pinia 3, vue-router 4). `openapi-typescript` 7 формально просит TS 5 (предупреждение peer), генерация работает.
- Среда разработки: Makefile рассчитан на Linux-оболочку. На Windows — WSL2 (в Ubuntu 24.04 уже есть `make`, `uv`, Python 3.12; нужны Node и pnpm).
