# Как писать код в этом проекте

Для агента и человека, которые пишут код. Короткая выжимка — в [AGENTS.md](../../AGENTS.md), раздел 4; здесь — подробности и причины. Требования — в [SPEC](../SPEC.md), этот документ их не заменяет.

Правило чтения: если пункт мешает сделать задачу — не обходить молча, а записать вопрос в [status.md](../status.md) и предложить правку этого документа.

## 1. Прежде чем писать

1. Прочитать в `docs/status.md`, какой этап идёт и что занято. Прочитать этап в SPEC §21 и разделы, на которые он ссылается.
2. Найти в карте изменений (AGENTS.md, раздел 3), где это правится и что обновляется вместе с кодом.
3. Прочитать README модуля, который меняешь. Нет README — значит, модуля ещё нет: создать его по шаблону SPEC §19.3.
4. Писать только то, что нужно текущему этапу. Заготовки «на вырост» и абстракции под будущие этапы не делать: SPEC меняется, а лишний код остаётся.

## 2. Факты проверять, а не вспоминать

Это главный источник ошибок в проекте, поэтому отдельным разделом.

- **WeKnora.** Всё, что утверждается о её поведении, — маршрут, роль, колонка, настройка, формат — проверяется по коду в `weknora/` на закреплённом теге, а не по памяти и не по SPEC. WeKnora выходит каждые 2–3 недели, знания модели о ней устарели. Проверка — `git -C weknora grep -n '<что ищем>'`; в коммите или в README модуля указать файл, на который опирается решение.
- **Сверка уже находила расхождения.** Закреплённый коммит оказался не релизом; миграция в форке ломала бы обновления; у сотрудника оказалось право создавать своих агентов (ADR 0013, 0014). Если код WeKnora противоречит SPEC — это находка: записать в `status.md`, не подгонять код под SPEC.
- **Библиотеки.** Версии в lock-файлах новее того, что помнит модель. API берётся из установленного пакета (`node_modules/<пакет>`, `uv run python -c "import x; help(x.y)"`), а не из памяти. Пример: TypeScript 7 уже вышел и несовместим с `vue-tsc`.
- **«Работает» — значит запускалось.** В отчёте и в `status.md` разделять «проверено запуском», «проверено только статически» и «не проверено». Критерий этапа отмечается выполненным только после прогона демо-сценария.

## 3. Границы системы

Нарушение любого пункта — ошибка архитектуры, а не стиля.

| Нельзя | Потому что | Как правильно |
| --- | --- | --- |
| Менять файлы в `weknora/` без строки в реестре | Каждый патч переносится вручную при каждом обновлении | Порядок выбора: конфигурация и API → MCP или nginx → свой сервис → патч (SPEC §2.4) |
| Добавлять миграции в форк WeKnora | Нумерация сквозная, апстримная миграция с тем же номером будет молча пропущена (ADR 0014) | Свои таблицы — в схеме `corp`; правки объектов WeKnora — шагом `provision` |
| Писать в таблицы WeKnora | Её код не ждёт чужих записей; схема меняется без предупреждения | Через API WeKnora. Четыре исключения перечислены в SPEC §16.2; каждое — одна именованная функция в `modules/weknora/` с записью в аудит |
| Читать таблицы WeKnora из произвольного модуля | При обновлении надо сверить схему в одном месте | Только через `modules/weknora/`, с явным списком колонок и тестом на схему |
| Брать пользователя из тела запроса или из аргументов, которые прислала модель | Это подмена личности | Только из проверенного JWT WeKnora или подписанного заголовка `X-Corp-User` |
| Опираться на системный промпт агента как на защиту | Сотрудник может его прочитать и создать своего агента (ADR 0013) | Проверки — на сервере: права, guard-модель, RLS |
| Буферизовать поток ответа чата | Пропадает стриминг, растёт время до первого токена | Прокси в `corp-ext` и nginx пропускают поток как есть |
| Ходить в сеть наружу, подключать CDN и внешние шрифты | Сервер будет без интернета (SPEC §18.3) | Всё локально; зависимости — из lock-файлов и офлайн-бандла |

## 4. Python: `corp-ext`, `data-gateway`, `fake-llm`

### Устройство модуля

```text
app/modules/<имя>/
  README.md      # по шаблону SPEC §19.3 — проверяется make docs-check
  router.py      # маршруты FastAPI: разбор запроса, права, вызов сервиса, ответ. Без бизнес-логики
  service.py     # бизнес-логика. Не импортирует FastAPI, принимает сессию БД и клиентов аргументами
  models.py      # таблицы SQLAlchemy схемы corp
  schemas.py     # модели Pydantic для API
  tasks.py       # фоновые задачи taskiq (ADR 0015)
```

Файл создаётся, когда он нужен. Модули зовут друг друга через `service.py`, а не через чужие `models.py`.

### Правила

- **Конфигурация** — только через `Settings` (`app/core/config.py`), переданный зависимостью. `os.environ` в модулях не читать. Новый ключ: поле в модели настроек с описанием, строка в `config/corp-ext.example.yaml`, тест. Неизвестные ключи запрещены (`extra="forbid"`) — опечатка в конфиге должна останавливать запуск.
- **Секреты** — из файла секрета или переменной окружения, тип `SecretStr`. Не в YAML, не в логах, не в сообщениях исключений, не в `repr`.
- **База.** Таблицы только в схеме `corp`, наследуются от `Base`. Каждое изменение схемы — миграция Alembic с рабочим `downgrade`; перенос данных — отдельной миграцией от изменения схемы. Новый `models.py` регистрируется в `app/core/model_registry.py`, иначе Alembic не увидит таблицы; тест `test_model_registry` это ловит.
- **SQL** — только с параметрами. Склейка строк и f-строки с данными запрещены; имена схем и таблиц — только из констант.
- **Время** — в БД `timestamptz` в UTC, в коде — `datetime` с часовым поясом. Часовой пояс компании используется только для границ окон лимитов и для показа.
- **Асинхронность.** В обработчиках и задачах нет блокирующих вызовов. Синхронные библиотеки (`ldap3`, `python-docx`, `openpyxl`) — через `asyncio.to_thread`; внешние программы (pandoc, LibreOffice) — через `asyncio.create_subprocess_exec` с тайм-аутом.
- **Внешние вызовы** (WeKnora, Keycloak, vLLM, AD, MS SQL) — всегда с тайм-аутом, клиент переиспользуется. Повтор — только для идемпотентных операций.
- **Идемпотентность.** Синхронизация, раскладка и шаги `provision` безопасно запускаются повторно и продолжают после сбоя на середине. У всего, что меняет доступ, есть `--dry-run`. Источник членства трогает только свои записи (SPEC §7.3).
- **Права и аудит.** У каждого эндпоинта админки — зависимость с конкретным правом (`admin.chats.view`) и проверка владения ресурсом. Любое действие админа над чужими данными пишет строку в `corp.audit_log` в той же транзакции.
- **Ошибки API** — единый формат `{"code": "limit_exceeded", "message": "…", "details": {…}}`: `code` стабилен и на английском, `message` — на русском и пригоден для показа пользователю. Внутренние детали и трассировки в ответ не попадают.
- **Логи** — structlog: имя события в `snake_case` плюс поля (`log.info("sync_finished", users=312, duration_ms=840)`), без склейки в строку. На уровне INFO нет текстов сообщений пользователей, токенов, паролей. Логи идут в stdout, поэтому команды CLI, печатающие данные в stdout, приглушают логи.
- **Redis** — свой номер БД, ключи с префиксом `corp:`; всё, что должно быть атомарным (счётчики лимитов, слоты), — скриптом Lua, а не парой команд.
- **Типы** — `mypy --strict`. `Any` не выпускать за границу функции; `# type: ignore[код]` и `# noqa: КОД` — только с кодом и причиной в той же строке.
- **Комментарии** — по-русски и о том, *почему* так, а не *что* делает строка. Идентификаторы — по-английски.
- **Промпты** — в файлах, а не в строках посреди кода; на русском или английском, с `{{language}}`, без китайских примеров (SPEC §13.4).

### Тесты

- Unit-тесты не ходят в сеть и не читают конфиг разработчика — за этим следит фикстура в `tests/conftest.py`.
- Postgres и Redis в интеграционных тестах — настоящие (testcontainers), а не моки: проверяются миграции, Lua и SQL. Такие тесты помечаются `@pytest.mark.integration` и требуют Docker.
- Ответы модели — через `fake-llm` с маркером сценария, чтобы тест был детерминированным. Нужен новый вариант ответа — добавить сценарий в `fake-llm`, а не мок в тесте.
- Тесты безопасности из SPEC §20.2 — часть задачи, которая вводит соответствующую функцию, а не отдельная работа «потом».
- Ошибка сначала воспроизводится тестом, потом исправляется.
- Тест, линт или проверку типов нельзя ослаблять, чтобы стало зелёным. Если проверка неверна — исправить её отдельным коммитом с объяснением.

## 5. Фронтенд: `corp-admin` и патчи фронтенда WeKnora

- Строки интерфейса — только через i18n (`src/i18n/locales/ru.ts`). Тест проверяет отсутствие иероглифов; строк на русском прямо в шаблонах быть не должно.
- Новая страница — три места: файл в `src/pages/`, маршрут в `src/router/index.ts`, пункт в `src/router/navigation.ts`. Плюс право в `docs/reference/permissions.md` и проверка этого права на сервере: скрытый пункт меню — не защита.
- Запросы к API — только через сгенерированный клиент `src/api/client.ts`. `openapi.json` и `schema.d.ts` руками не правятся: поменял маршрут или схему в `corp-ext` — `make gen-api`, оба файла в тот же коммит. Иначе `make docs-check` красный.
- Сначала компоненты TDesign, свои — когда готового нет. Стили — `scoped`, без inline-стилей и inline-скриптов (CSP, SPEC §17.1).
- Мажорные версии библиотек — как у `weknora/frontend/package.json`. Обновление «до последней» ломает единый стек; TypeScript 7 не ставить.
- Ответы модели и любой чужой HTML вставляются только после санитизации; `v-html` с непроверенным содержимым запрещён.

## 6. Патчи WeKnora

Подробная инструкция появится в `write-weknora-patch.md`; пока — правила.

- До патча убедиться, что нельзя обойтись конфигурацией, API, MCP, nginx или своим сервисом, и записать это в ADR.
- Минимальный дифф: не переформатировать, не переименовывать, не трогать соседний код. Чем меньше строк, тем дешевле перенос при обновлении.
- Поведение включается флагом или настройкой; без неё WeKnora работает как раньше. Так патч можно отправить в апстрим.
- Один патч — один коммит `P-NN: …` в ветке `corp/v<версия>` форка, тест в стиле WeKnora рядом, строка в `docs/patches.md`.
- Пока форка во внутреннем git нет, в подмодуле ничего не коммитить. Указатель подмодуля в основном репозитории менять только осознанно и отдельным коммитом.

## 7. Инфраструктура

- Образы закрепляются (к проду — по digest), у каждого сервиса healthcheck, лимиты и `restart: unless-stopped`.
- Заглушка должна падать громко и говорить, на каком этапе появится реализация, как цели-заглушки в `Makefile`. Заглушка, которая молча возвращает успех, — скрытая ошибка.
- Файлы — с окончаниями строк LF (`.gitattributes`). На Windows работать из WSL2; виртуальные окружения Windows и WSL в одном каталоге не смешивать.
- Команду, которая упала при проверке, сначала диагностировать. Не подбирать флаги, пока не стало зелёным.

## 8. Коммиты и отчёт

- Маленькие коммиты в стиле Conventional Commits, сообщения на английском; каждый собирается и проходит `make check`.
- Сгенерированное (`openapi.json`, `schema.d.ts`, lock-файлы, справочники в `docs/reference/`) коммитится вместе с изменением, которое его породило.
- В `main` вливает человек. Агент работает в ветке `agent/<задача>` и не пушит без просьбы.
- Definition of Done — AGENTS.md, раздел 6. В `status.md` — что сделано, что не проверено и почему, какие вопросы возникли.
- Изменилось требование — сначала правка SPEC и запись в CHANGELOG, потом код. Код, который расходится со SPEC без записи, считается ошибкой.
